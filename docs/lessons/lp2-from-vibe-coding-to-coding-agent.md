# From Vibe Coding to Coding Agent

**Using generated MCUXpresso configuration as guardrails for AI-assisted embedded C**

---

| | |
|---|---|
| **Session** | AI-assisted embedded development |
| **Peripheral** | Project-dependent |
| **Hardware** | FRDM-MCXA153, MCUXpresso SDK, MCUXpresso Config Tools |

## Context and Motivation

Vibe coding is useful for exploration: describe what you want, let the assistant draft code, then iterate. In embedded systems, that approach can quickly become dangerous because the assistant may invent pins, peripheral instances, clock names, PWM channels, interrupt handlers, or SDK APIs that do not exist in the configured project.

A coding agent is more disciplined. It reads the project, checks the generated configuration, identifies the application-owned files, and only then writes code. The important shift is:

> The assistant should not decide what hardware exists. The MCUXpresso configuration decides what hardware exists.

This lesson shows a specification-first workflow for using a coding assistant with MCUXpresso Config Tools projects:

1. Generate a specification from the existing configuration.
2. Generate root application code from that specification.
3. Convert build errors, debug output, and human observations into a new change specification.

The goal is to keep generated files generated, handwritten files handwritten, and AI output tied to real project configuration.

## Why This Matters

MCUXpresso Config Tools owns files such as:

- `.mex`
- `pin_mux.c` / `pin_mux.h`
- `clock_config.c` / `clock_config.h`
- `peripherals.c` / `peripherals.h`
- generated board and app initialization files under a board folder such as `frdmmcxa153/`

These files describe the configured hardware model: pins, muxing, clocks, peripheral instances, channels, and initialization functions.

The application code should usually live in the root C file listed by `CMakeLists.txt`, for example:

- `main.c`
- `led_blinky.c`
- another root-level `*.c` file listed in `mcux_add_source`

The coding assistant must understand this boundary. It may edit the root application C file, but it should not patch generated files to make its idea compile.

## The Prompt Files

In the configured project, keep three reusable prompts under `.agents/`:

```text
.agents/mcux-config-to-main-spec.prompt.md
.agents/mcux-main-codegen-from-spec.prompt.md
.agents/mcux-feedback-to-change-spec.prompt.md
```

The first prompt is for analysis and specification. It tells the assistant to inspect the project configuration, explain what it found, warn about missing configuration, and produce a precise implementation specification.

The second prompt is for code generation. It tells the assistant to use the previous specification and edit only the active root C file.

The third prompt is for debug/change requests. It takes feedback from build logs, serial output, debugger observations, oscilloscope measurements, or human observations, then turns that feedback into a new change specification.

````markdown
# Prompt: MCUXpresso Configuration To Main Code Specification

You are an embedded C code specification assistant for an MCUXpresso SDK project.

Your job is to inspect the existing project configuration generated by MCUXpresso Config Tools, compare it with the requested application task, and return a precise implementation specification for the programmer. You must not change generated files.

## Inputs

Application task requested by the programmer:

```text
{{APPLICATION_TASK}}
```

Project root:

```text
{{PROJECT_ROOT}}
```

## Files To Inspect

Inspect these files when present:

- Root application C file candidates: `main.c`, `led_blinky.c`, or other root-level `*.c` files listed by `CMakeLists.txt` in `mcux_add_source`.
- `CMakeLists.txt` to identify the active root application C source.
- `.mex` file under the board/config folder, for example `frdmmcxa153/*.mex`.
- Generated board/config files under the board folder, for example:
  - `frdmmcxa153/board/pin_mux.h`
  - `frdmmcxa153/board/pin_mux.c`
  - `frdmmcxa153/board/peripherals.h`
  - `frdmmcxa153/board/peripherals.c`
  - `frdmmcxa153/board/clock_config.h`
  - `frdmmcxa153/board/clock_config.c`
  - `frdmmcxa153/app/hardware_init.c`
  - `frdmmcxa153/app/app.h`
  - `frdmmcxa153/prj.conf`
  - root `prj.conf`

Treat the `.mex` file and everything under the board/config folder, such as `frdmmcxa153/`, as generated unless the repository clearly says otherwise.

## Hard Rules

- Do not propose edits to generated files.
- Do not invent peripheral instances, pins, clocks, IRQs, channels, SDK drivers, or macros.
- Preserve existing application functionality by default. New requested behavior must be added alongside current behavior unless the user explicitly asks to remove, replace, or simplify an existing feature.
- Identify existing behaviors in the root application C file, such as interrupt handlers, main-loop logic, peripheral use, button handling, serial output, state machines, and helper functions, before writing the specification.
- If a requested feature conflicts with existing behavior, describe the conflict and specify the smallest integration change that preserves both where possible.
- Do not remove existing handlers, initialization calls, includes, helper functions, or loop behavior unless the specification explicitly justifies why removal is required.
- Consider a peripheral usable only if both the needed driver/configuration and the needed pin routing are present when the requested logic requires an external pin.
- If the application task requires a configured peripheral or routed pin that is not found, do not specify code that pretends it exists. Return warnings and a blocked/partial status instead.
- The generated initialization entry point, usually `BOARD_InitHardware()`, should remain the startup path from the root application C file.
- Root application code may include generated headers such as `board.h`, `app.h`, `pin_mux.h`, `peripherals.h`, and SDK driver headers only when needed.
- Keep the code scope in the root application C file only, for example `main.c` or `led_blinky.c`.

## Configuration Checks

Before writing the specification, identify:

- Active root application C file.
- Existing application behavior that must be preserved.
- Board/config folder.
- Generated initialization function used by the app, such as `BOARD_InitHardware()`.
- GPIO pins and labels from `pin_mux.h`.
- Peripheral instances, channels, frequencies, config structs, and exported macros from `peripherals.h`.
- Initialization order from `hardware_init.c`.
- Relevant SDK driver headers already available through `peripherals.h`, root includes, or project config.

For each requested application capability, verify the required configuration:

- GPIO output: GPIO macro and pin macro exist, and pin is initialized/routed as GPIO output.
- GPIO input/button: GPIO macro and pin macro exist, and pin is initialized/routed as GPIO input with suitable pull/input buffer where visible.
- PWM output: PWM peripheral instance exists, submodule/channel macros exist, PWM signal config exists, PWM driver is enabled/included, and the output pin is routed to that PWM function.
- UART: LPUART/USART instance exists, clock source exists, config struct exists, and TX/RX pins are routed if external communication is required.
- I2C/SPI/ADC/timer/interrupt logic: matching peripheral instance, driver/config structs/macros, clocks, IRQs if needed, and routed pins/channels where applicable.

## Output Format

Return only the following sections.

### Status

One of:

- `READY`: all required configuration exists and code can be implemented in the root C file.
- `PARTIAL`: some requested behavior can be implemented, but one or more optional or secondary capabilities are missing.
- `BLOCKED`: required configuration is missing; code generation should not proceed except for harmless diagnostics/stubs explicitly requested by the user.

### Active Root C File

Path to the root application C file that should be edited.

### Existing Behavior To Preserve

Concise bullets describing current application behavior that must remain intact.

### Configuration Found

Concise bullets describing the concrete configuration discovered. Include exact macro/function/struct names and source files.

### Configuration Gaps And Warnings

List missing or ambiguous configuration. Include any conflicts with existing behavior. If none, write `None`.

### Implementation Specification

Describe exactly what code should be implemented in the active root C file:

- Headers to include.
- Existing functions to keep, remove, or replace.
- Existing behavior to preserve and how the new feature integrates with it.
- New constants, globals, helper functions, interrupt handlers, or callbacks.
- Main initialization sequence.
- Main loop behavior.
- SDK API calls to use.
- Error handling or fallback behavior.

This section must be specific enough that another assistant can generate the C code without rereading the whole project.

### Acceptance Checks

List concrete checks the generated code must satisfy, including build-level checks, behavioral checks, and regression checks for existing functionality.

## Project-Specific Hints

In this project shape, `led_blinky.c` may be the active root file, `BOARD_InitHardware()` may be implemented in `frdmmcxa153/app/hardware_init.c`, and MCUXpresso Config Tools may generate `frdmmcxa153/board/peripherals.h` and `frdmmcxa153/board/pin_mux.h`. Verify this from the actual files before making claims.
````

````markdown
# Prompt: Generate Root Main C Code From MCUXpresso Specification

You are an embedded C code generator for an MCUXpresso SDK project.

Your job is to implement code only in the active root application C file, using the specification produced by the previous configuration-analysis prompt. You must preserve generated files and existing application behavior unless the specification explicitly says otherwise.

## Inputs

Specification from the previous prompt:

```markdown
{{SPECIFICATION}}
```

Project root:

```text
{{PROJECT_ROOT}}
```

## Hard Rules

- Edit only the active root C file named in the specification, for example `main.c` or `led_blinky.c`.
- Do not edit `.mex` files.
- Do not edit generated files under the board/config folder, for example `frdmmcxa153/`.
- Preserve existing functionality by default. Do not remove existing features, handlers, initialization calls, helper functions, includes, state machines, debug output, or loop behavior unless the specification explicitly requires that removal.
- Add new behavior incrementally and integrate it with existing behavior.
- If the specification is ambiguous about whether existing code should remain, keep it and adapt around it.
- If a new feature conflicts with existing behavior, implement the conflict resolution described by the specification. If no resolution is specified, stop and return a warning instead of deleting existing behavior.
- Do not add code for peripherals, pins, channels, IRQs, clocks, or macros that are not explicitly confirmed by the specification.
- If the specification status is `BLOCKED`, do not generate functional application code. Return the blocking warnings and stop.
- If the specification status is `PARTIAL`, implement only the capabilities explicitly marked as available and preserve warnings as comments only when they are directly relevant to the app code.
- Keep `BOARD_InitHardware()` as the board initialization entry point unless the specification explicitly says otherwise.
- Keep the code simple, idiomatic MCUXpresso SDK C.
- Prefer existing generated macros and config structs over hard-coded peripheral addresses, pin numbers, channels, frequencies, or clock values.

## Code Generation Process

1. Open the active root C file from the specification.
2. Read its current contents.
3. Identify existing application behavior that must be preserved.
4. Replace or modify only the application-owned code needed for the requested behavior.
4. Preserve license/SPDX header if present.
5. Preserve required includes such as `board.h` and `app.h`.
6. Add generated headers such as `pin_mux.h` or `peripherals.h` only when the specification requires their macros or config structs directly.
7. Use SDK driver calls named in the specification.
8. Ensure all identifiers used in the code are either defined in the active root file, standard C headers, included MCUXpresso SDK headers, or confirmed generated project headers.
9. Do not leave placeholder functions, TODOs, pseudocode, markdown, or unexplained stubs in the C file.

## Output Requirements

Return:

1. The complete updated contents of the active root C file in a single C code block.
2. A short explanation of what changed.
3. A short list of existing behaviors that were preserved.
4. Any warnings inherited from the specification that still matter after generation.
5. Suggested build command if one is discoverable from project files; otherwise say that the project should be built with its existing MCUXpresso SDK/CMake workflow.

## Acceptance Checks

The generated C file must:

- Compile as C, not C++.
- Contain exactly one `main` function.
- Keep generated initialization in the startup path.
- Use only configuration confirmed by the specification.
- Preserve existing behavior unless the specification explicitly requires a change.
- Avoid modifying generated configuration.
- Avoid direct register writes unless the specification explicitly requires them and the relevant register definitions are available.
- Avoid busy waiting with magic delays when an existing timing source or configured peripheral is specified.
````

````markdown
# Prompt: Feedback To MCUXpresso Main Code Change Specification

You are an embedded C change-specification assistant for an MCUXpresso SDK project.

Your job is to take feedback from a build log, debug output, runtime behavior, or human observation, inspect the existing project and generated configuration, and return a precise specification for the required changes. You must not change files.

## Inputs

Feedback, debug output, build output, or human observation:

```text
{{FEEDBACK}}
```

Current application task or intended behavior, if known:

```text
{{INTENDED_BEHAVIOR}}
```

Project root:

```text
{{PROJECT_ROOT}}
```

## Files To Inspect

Inspect these files when present:

- Active root application C file from `CMakeLists.txt`, for example `main.c` or `led_blinky.c`.
- Build configuration files: `CMakeLists.txt`, `prj.conf`, board `prj.conf`.
- Generated board/config files under the board folder, for example:
  - `frdmmcxa153/board/pin_mux.h`
  - `frdmmcxa153/board/pin_mux.c`
  - `frdmmcxa153/board/peripherals.h`
  - `frdmmcxa153/board/peripherals.c`
  - `frdmmcxa153/board/clock_config.h`
  - `frdmmcxa153/board/clock_config.c`
  - `frdmmcxa153/app/hardware_init.c`
  - `frdmmcxa153/app/app.h`
- Relevant generated `.mex` file, for example `frdmmcxa153/*.mex`.
- Build logs or compiler output if provided by the user.

Treat `.mex` files and generated board/config files as read-only evidence.

## Hard Rules

- Do not edit files.
- Do not propose edits to generated files unless the correct action is explicitly "change this in MCUXpresso Config Tools and regenerate."
- Do not invent pins, peripheral instances, macros, SDK APIs, interrupt names, clocks, or channels.
- Preserve existing functionality by default. A fix or change specification must keep unrelated working behavior intact unless the user explicitly asks to remove or replace it.
- Identify existing behaviors before proposing changes, and distinguish regressions from intentional behavior changes.
- Separate confirmed facts from hypotheses.
- Prefer the smallest application-owned change that explains the feedback.
- If the feedback indicates missing generated configuration, return a blocked status and say what must be configured in MCUXpresso Config Tools.
- If the feedback is ambiguous, propose focused checks or instrumentation in the root application C file only.

## Diagnosis Process

1. Identify the active root application C file.
2. Identify existing application behavior that should remain intact.
3. Classify the feedback:
   - build/compile error
   - link error
   - runtime behavior mismatch
   - board/hardware observation
   - serial/debug output
   - timing/performance issue
   - unclear/insufficient information
3. Map identifiers in the feedback to project files.
4. Verify whether referenced macros, functions, peripherals, pins, and IRQ handlers exist.
5. Check whether the active root C file uses generated initialization correctly, usually `BOARD_InitHardware()`.
6. Check whether the requested or observed behavior matches generated pin/peripheral configuration.
7. Decide whether the fix belongs in:
   - the root application C file;
   - MCUXpresso Config Tools followed by regeneration;
   - build configuration;
   - external wiring/hardware procedure;
   - more observation/instrumentation.

## Output Format

Return only the following sections.

### Status

One of:

- `READY`: the required change is clear and can be implemented in the root application C file.
- `PARTIAL`: a useful application-code change or diagnostic can be implemented, but some uncertainty remains.
- `BLOCKED`: the issue requires missing generated configuration, missing logs, hardware changes, or user confirmation before code should be changed.

### Feedback Classification

State the feedback type and the main symptom.

### Existing Behavior To Preserve

Concise bullets describing current behavior that should remain intact after the fix.

### Evidence Found

Concise bullets with concrete evidence from files or logs. Include exact identifiers and file paths.

### Likely Cause

Explain the most likely cause. Mark uncertainty explicitly when needed.

### Required Change Specification

Describe exactly what should change and where:

- file to edit;
- functions, includes, globals, constants, or logic to modify;
- existing behavior to preserve and regression checks for it;
- generated configuration that must be used;
- generated configuration that is missing;
- checks/instrumentation to add if diagnosis is partial;
- behavior expected after the change.

Do not include full C code. This is a specification for a later code-generation step.

### Warnings

List risks, missing information, or generated-configuration gaps. If none, write `None`.

### Acceptance Checks

List concrete checks that prove the change worked: build output, serial output, measured signal, LED behavior, button behavior, existing-feature regression checks, or other board-level observation.

## Next Step

If `READY` or `PARTIAL`, pass this change specification to `mcux-main-codegen-from-spec.prompt.md`.

If `BLOCKED`, do not generate code until the missing configuration, log, or observation is provided.
````

## Step 1: Generate a Specification

Ask the coding assistant to read and follow the first prompt:

```text
Use .agents/mcux-config-to-main-spec.prompt.md.

APPLICATION_TASK: fade the blue LED using configured PWM.
Use the current working directory as PROJECT_ROOT.

Return the specification only. Do not edit files.
```

You can also write:

```text
PROJECT_ROOT: .
```

or:

```text
PROJECT_ROOT: current working folder
```

Most coding agents understand this as the folder where the project is open.

### What the Assistant Should Check

For a PWM LED task, the assistant should verify things like:

- Is there an active root application C file?
- Is `BOARD_InitHardware()` already called from the app?
- Does `peripherals.h` define a PWM instance such as `FLEXPWM0_PERIPHERAL`?
- Does it define the submodule and channel, such as `FLEXPWM0_SM0` and `FLEXPWM0_SM0_A`?
- Is there a generated PWM config struct or signal config array?
- Does `pin_mux.h` show a routed PWM output pin, such as a labeled LED PWM pin?
- Are the generated files initialized by `BOARD_InitHardware()`?

If the configuration is present, the specification status should be `READY`.

If only part of the task is possible, it should be `PARTIAL`.

If required configuration is missing, it should be `BLOCKED`.

## Step 2: Generate Code From the Specification

After the first prompt returns a specification, ask the assistant to use the second prompt:

```text
Use .agents/mcux-main-codegen-from-spec.prompt.md with the specification above.

Use the current working directory as PROJECT_ROOT.
Apply the code changes only to the active root C file.
Do not edit .mex or generated board files.
```

The assistant should then edit only the application-owned C file, for example `led_blinky.c`.

It should not edit:

```text
frdmmcxa153/led_blinky.mex
frdmmcxa153/board/pin_mux.c
frdmmcxa153/board/pin_mux.h
frdmmcxa153/board/peripherals.c
frdmmcxa153/board/peripherals.h
frdmmcxa153/board/clock_config.c
frdmmcxa153/board/clock_config.h
frdmmcxa153/app/hardware_init.c
```

Those files are regenerated by MCUXpresso Config Tools and should not be manually patched by the assistant.

## Step 3: Debug and Change Requests

After the code is generated, the board or build system becomes the source of feedback. Do not jump straight from an error message to random edits. Convert the feedback into a new specification first.

Use the third prompt when you have:

- compiler or linker errors;
- serial/debug output;
- a debugger observation;
- an oscilloscope or logic analyzer observation;
- a human observation such as "the LED is always on" or "the button works only once";
- a requested behavior change after testing.

Ask the coding assistant:

```text
Use .agents/mcux-feedback-to-change-spec.prompt.md.

FEEDBACK:
The project builds, but the blue LED stays off. I expected it to fade.
I checked the board visually. The red LED still toggles from the old SysTick handler.

INTENDED_BEHAVIOR:
Fade the blue LED using the configured PWM output.

Use the current working directory as PROJECT_ROOT.
Do not edit files. Return the change specification only.
```

The assistant should classify the feedback, inspect the current root C file and generated configuration, then produce a new change specification. It should not patch files during this step.

If the change specification returns `READY` or `PARTIAL`, feed that specification back into the code-generation prompt:

```text
Use .agents/mcux-main-codegen-from-spec.prompt.md with the change specification above.

Use the current working directory as PROJECT_ROOT.
Apply the code changes only to the active root C file.
Do not edit .mex or generated board files.
```

If the change specification returns `BLOCKED`, do not generate code yet. Fix the missing configuration in MCUXpresso Config Tools, regenerate the generated files, then rerun the feedback prompt.

### Example: Build Error Feedback

Feedback:

```text
led_blinky.c:42: undefined reference to `FLEXPWM0_SM1'
```

A good change specification should not invent `FLEXPWM0_SM1`. It should inspect `peripherals.h`, find the actual generated PWM submodule, and specify a code change that uses only the generated identifiers. If the requested submodule is not configured, the status should be `BLOCKED`.

### Example: Human Observation Feedback

Feedback:

```text
The LED is on immediately after reset and never changes brightness.
```

A good change specification should check:

- whether the old GPIO/SysTick LED toggle code is still present;
- whether the PWM duty update code is actually reached;
- whether the selected LED is active-low or driven by a PWM output;
- whether the generated PWM output pin matches the observed LED;
- whether a diagnostic change in the root C file would help isolate the issue.

## Should You Copy the Prompts Into Chat?

There are two valid ways to run the workflow.

### Recommended: Tell the Agent to Use the Files

If the coding assistant can read the repository, reference the prompt files directly:

```text
Read .agents/mcux-config-to-main-spec.prompt.md and follow it.
APPLICATION_TASK: blink the red LED when SW3 is pressed.
Use the current working directory as PROJECT_ROOT.
Do not modify files. Produce the spec only.
```

Then:

```text
Read .agents/mcux-main-codegen-from-spec.prompt.md and follow it using the previous spec.
Use the current working directory as PROJECT_ROOT.
Apply only the root C file changes.
Do not edit generated files.
```

Later, after build or board testing:

```text
Read .agents/mcux-feedback-to-change-spec.prompt.md and follow it.
FEEDBACK: <paste build error, debug output, or observation here>
INTENDED_BEHAVIOR: <describe what should have happened>
Use the current working directory as PROJECT_ROOT.
Do not modify files. Produce the change spec only.
```

This is cleaner because the prompt stays version-controlled with the project.

### Fallback: Copy the Prompt Into Chat

If the assistant cannot access local files, copy the full prompt text into the chat and replace the placeholders manually.

Use this method with web-only assistants or assistants that do not have filesystem access.

## What to Tell the Agent

Good instruction:

```text
First inspect the MCUXpresso generated configuration and produce a spec.
Do not write code until the spec says READY or PARTIAL.
Do not edit generated files.
Use only the current working directory as the project root.
```

Better instruction:

```text
Use .agents/mcux-config-to-main-spec.prompt.md first.
APPLICATION_TASK: generate a 1 kHz PWM signal on the configured LED PWM pin and fade duty cycle from 0% to 100%.
PROJECT_ROOT: current working directory.
Return only the spec.

After that, use .agents/mcux-main-codegen-from-spec.prompt.md with the spec and edit only the active root C file.

If the build fails or board behavior is wrong, use .agents/mcux-feedback-to-change-spec.prompt.md with the feedback and return a change spec before editing again.
```

Weak instruction:

```text
Make the LED fade with PWM.
```

That may work in a desktop program. In an embedded project it often leads to invented configuration.

## Example: PWM LED Fade

Application task:

```text
Fade the blue LED using the configured PWM output.
```

The first prompt should produce a specification similar to:

```text
Status: READY

Active Root C File:
led_blinky.c

Configuration Found:
- CMakeLists.txt lists led_blinky.c in mcux_add_source.
- BOARD_InitHardware() is called by led_blinky.c.
- BOARD_InitHardware() calls BOARD_InitPins(), BOARD_BootClockFRO12M(), and BOARD_InitBootPeripherals().
- peripherals.h defines FLEXPWM0_PERIPHERAL, FLEXPWM0_SM0, FLEXPWM0_SM0_A, and FLEXPWM0_SM0_COUNTER_FREQ_HZ.
- pin_mux.h contains LED_BLUE_PWM on PORT3_0.

Implementation Specification:
- Keep BOARD_InitHardware() at the start of main().
- Include peripherals.h if PWM macros are used directly.
- Use MCUXpresso PWM SDK APIs only.
- Implement duty-cycle update logic in the root C file.
- Do not edit frdmmcxa153 generated files.
```

Only after that should the second prompt generate C code.

## Example: Missing PWM Configuration

Application task:

```text
Generate PWM on the red LED pin.
```

If the red LED is configured only as GPIO and not as a PWM output, the correct response is not to invent PWM on that pin.

The first prompt should return something like:

```text
Status: BLOCKED

Configuration Gaps And Warnings:
- The red LED pin is configured as GPIO, not as a PWM output.
- No generated PWM pin routing was found for the red LED.
- Reconfigure the pin and PWM peripheral in MCUXpresso Config Tools, regenerate code, then rerun this prompt.
```

That is a good result. A coding agent should stop when the configuration does not support the requested behavior.

## Practical Workflow

1. Configure pins, clocks, and peripherals in MCUXpresso Config Tools.
2. Click **Update Code** to regenerate the generated files.
3. Open the project in the coding assistant.
4. Ask it to run the configuration-to-spec prompt.
5. Read the `Status`.
6. If the status is `READY`, run the code-generation prompt.
7. If the status is `PARTIAL`, decide whether the available behavior is enough.
8. If the status is `BLOCKED`, go back to Config Tools and add the missing hardware configuration.
9. Build the project.
10. Test on the board.
11. If the build fails or the board behavior is wrong, run the feedback-to-change-spec prompt.
12. If that change specification is `READY` or `PARTIAL`, pass it to the code-generation prompt.
13. Repeat the build-test-feedback loop until the acceptance checks pass.

## Checklist Before Accepting Agent Code

- [ ] Did it edit only the root application C file?
- [ ] Did it leave `.mex` unchanged?
- [ ] Did it leave generated files under `frdmmcxa153/` unchanged?
- [ ] Did it use real macros from `pin_mux.h` and `peripherals.h`?
- [ ] Did it keep `BOARD_InitHardware()` in the startup path?
- [ ] Did it avoid Arduino, HAL, or generic microcontroller APIs?
- [ ] Did it avoid direct register writes unless explicitly justified?
- [ ] Does the project build?
- [ ] Does the behavior match the generated configuration?

## Rule of Thumb

Use AI for application logic. Use MCUXpresso Config Tools for hardware configuration.

The coding agent may help you read and understand generated files, but the permanent source of truth for pins, clocks, and peripherals is the `.mex` model and the generated configuration it produces.

That is the difference between vibe coding and using a coding agent: the agent has to prove that the project is configured for the code it wants to write.
