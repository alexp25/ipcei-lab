# LP0 - New Project Template

**Creating an intuitive FRDM-MCXA153 project template that still works with MCUXpresso Config Tools**

---

| | |
|---|---|
| **Board** | FRDM-MCXA153 |
| **SDK style** | MCUXpresso SDK v2 freestanding application |
| **Build system** | CMake + Ninja + ARM GCC |
| **Config tool** | MCUXpresso Config Tools: Pins, Clocks, Peripherals |
| **Template project** | `src/lab_new_project/new` |
| **Goal** | A clean starting project where generated files are easy to find and are the same files compiled by CMake |

## Context

![New Project Wizard selecting FRDM-MCXA153](../img/labp1/1_create_new_project.png)

*Figure 1. Creating the initial project from the MCUXpresso SDK New Project Wizard, selecting the FRDM-MCXA153 board, ARM GNU toolchain, and opening MCUXpresso Config Tools after creation.*

The initial project was created from the NXP `led_blinky_peripheral` example for `frdmmcxa153`. It built correctly, but its structure was confusing for a teaching template because generated files were split across several folders.

The project also behaved unexpectedly with MCUXpresso Config Tools: changing SysTick in the tool updated generated files in one location, while CMake still compiled older files from another location.

This document records the problem, the reason it happened, and the normalized structure used for the new project template.

## Original Problem

![Inspecting the generated project structure in VS Code](../img/labp1/2_explain_new_project_structure.png)

*Figure 2. Inspecting the generated project in VS Code. The initial project built, but the source tree required investigation because application files, board files, and generated files were not in one predictable location.*

The original project had generated and board-specific files spread across multiple locations:

```text
new/
|-- led_blinky/
|   |-- peripherals.c
|   `-- peripherals.h
|-- frdmmcxa153/
|   |-- led_blinky.mex
|   |-- board_files.cmake
|   |-- led_blinky/
|   |   |-- app.h
|   |   |-- hardware_init.c
|   |   |-- pin_mux.c
|   |   `-- pin_mux.h
|   `-- frdmmcxa153/
|       |-- board.c
|       |-- board.h
|       |-- clock_config.c
|       `-- clock_config.h
`-- led_blinky.c
```

This was hard to reason about because there were two folders named `led_blinky`, and the board name also appeared twice:

```text
new/led_blinky/
new/frdmmcxa153/led_blinky/
new/frdmmcxa153/frdmmcxa153/
```

Each folder had a different role, but that role was not obvious from the names.

## Symptom: SysTick Changes Did Not Apply

![SysTick configuration warning in MCUXpresso Config Tools](../img/labp1/3_check_missing_config.png)

*Figure 3. MCUXpresso Config Tools showed the SysTick configuration and code preview, but also reported project/toolchain warnings. This helped reveal that the tool was not fully synchronized with the actual CMake project layout.*

The user changed the SysTick reload period in MCUXpresso Config Tools. The `.mex` file showed the new value, and Config Tools generated files under:

```text
new/frdmmcxa153/board/
```

For example:

```text
new/frdmmcxa153/board/peripherals.c
new/frdmmcxa153/board/peripherals.h
```

However, the project was still compiling the old files:

```text
new/led_blinky/peripherals.c
new/led_blinky/peripherals.h
```

The old top-level `peripherals.h` still contained:

```c
#define SYSTICK_TICKS 12000000UL
```

while the file generated by Config Tools contained the new value:

```c
#define SYSTICK_TICKS 2400000UL
```

![Generated peripherals diff showing changed SysTick ticks](../img/labp1/4_check_updated_code.png)

*Figure 4. The Update Files comparison showed that Config Tools generated a changed `peripherals.h`, for example changing `SYSTICK_TICKS`. The important question was whether CMake was compiling this generated file or an older duplicate.*

So the source generated by Config Tools and the source compiled by CMake were not the same source.

## Root Cause

The project came from an exported/copied MCUXpresso SDK example. SDK examples usually combine several layers:

1. Application source files.
2. Board-specific support files.
3. Generated Pins/Clocks/Peripherals files.
4. CMake metadata.
5. MCUXpresso Config Tools metadata.

During export, the structure was partially flattened but not normalized. The `.mex` file expected generated files in this path:

```text
frdmmcxa153/board/
```

The relevant `.mex` entries were:

```xml
<file path="board/pin_mux.c" update_enabled="true"/>
<file path="board/pin_mux.h" update_enabled="true"/>
<file path="board/clock_config.c" update_enabled="true"/>
<file path="board/clock_config.h" update_enabled="true"/>
<file path="board/peripherals.c" update_enabled="true"/>
<file path="board/peripherals.h" update_enabled="true"/>
```

But `CMakeLists.txt` compiled peripherals from the top-level `led_blinky/` folder:

```cmake
mcux_add_source(
    SOURCES led_blinky/peripherals.c
            led_blinky/peripherals.h
)
```

Meanwhile, `frdmmcxa153/board_files.cmake` compiled pins and clocks from other folders:

```cmake
SOURCES frdmmcxa153/board.c
SOURCES frdmmcxa153/clock_config.c
SOURCES led_blinky/pin_mux.c
SOURCES led_blinky/hardware_init.c
```

Because `board_files.cmake` lives inside `frdmmcxa153/`, those paths resolved relative to `new/frdmmcxa153/`, not the project root. The result was a working build, but not an intuitive or tool-friendly template.

## Normalization Strategy

The fix was to make the file layout match the `.mex` file.

The canonical generated folder is now:

```text
new/frdmmcxa153/board/
```

This folder contains all files managed or expected by MCUXpresso Config Tools, plus board support headers used by those files.

Application-specific support that is not generated by Config Tools was moved to:

```text
new/frdmmcxa153/app/
```

The top-level application remains simple:

```text
new/led_blinky.c
```

## Normalized Project Structure

![Normalized project tree after applying Config Tools changes](../img/labp1/5_apply_changes.png)

*Figure 5. After normalization, the Explorer view shows the intended structure: generated/configured board files under `frdmmcxa153/board/`, handwritten app glue under `frdmmcxa153/app/`, and the main application at the project root.*

The normalized structure is:

```text
new/
|-- CMakeLists.txt
|-- CMakePresets.json
|-- Kconfig
|-- prj.conf
|-- example.yml
|-- mcux_include.json
|-- readme.md
|-- led_blinky.c
`-- frdmmcxa153/
    |-- led_blinky.mex
    |-- board_files.cmake
    |-- prj.conf
    |-- Kconfig.trace
    |-- app/
    |   |-- app.h
    |   `-- hardware_init.c
    `-- board/
        |-- board.c
        |-- board.h
        |-- clock_config.c
        |-- clock_config.h
        |-- pin_mux.c
        |-- pin_mux.h
        |-- peripherals.c
        |-- peripherals.h
        |-- FreeRTOSConfigBoard.h
        `-- se_board_config.h
```

![Code ownership diagram for the normalized template](../img/labp1/6_code_ownership_diagram.png)

*Figure 6. Code ownership in the normalized template. Application behavior is edited in C source files, app glue is maintained by the project, and generated board configuration is updated through MCUXpresso Config Tools.*

## Folder Roles

### `led_blinky.c`

This is the main application file. It contains `main()` and the SysTick interrupt handler:

```c
void SysTick_Handler(void)
{
    GPIO_PortToggle(BOARD_LED_GPIO, 1u << BOARD_LED_GPIO_PIN);
}

int main(void)
{
    BOARD_InitHardware();

    while (1)
    {
    }
}
```

The main loop is intentionally empty. The LED is toggled by the SysTick interrupt.

### `frdmmcxa153/led_blinky.mex`

This is the MCUXpresso Config Tools project file. It stores the Pins, Clocks, and Peripherals configuration.

When Config Tools generates code, it writes to:

```text
frdmmcxa153/board/
```

This is now also the folder compiled by CMake.

### `frdmmcxa153/board/`

This is the canonical board/config folder.

It contains generated files:

```text
pin_mux.c / pin_mux.h
clock_config.c / clock_config.h
peripherals.c / peripherals.h
```

It also contains board support files:

```text
board.c / board.h
FreeRTOSConfigBoard.h
se_board_config.h
```

Important rule:

> If MCUXpresso Config Tools updates Pins, Clocks, or Peripherals, the generated files in `frdmmcxa153/board/` are the files that CMake builds.

### `frdmmcxa153/app/`

This folder contains small app-level glue code that should not be regenerated by Config Tools.

`app.h` defines which board LED the application uses:

```c
#define BOARD_LED_GPIO     BOARD_LED_RED_GPIO
#define BOARD_LED_GPIO_PIN BOARD_LED_RED_GPIO_PIN
```

`hardware_init.c` defines the application initialization sequence:

```c
void BOARD_InitHardware(void)
{
    BOARD_InitPins();
    BOARD_BootClockFRO12M();
    BOARD_InitBootPeripherals();

    LED_RED_INIT(LOGIC_LED_OFF);
}
```

This means:

1. Configure pin mux.
2. Select the 12 MHz FRO clock setup.
3. Initialize generated peripherals, including SysTick.
4. Initialize the red LED as off.

## CMake Changes

The top-level `CMakeLists.txt` was simplified. It now adds only the main application source directly:

```cmake
mcux_add_source(
    SOURCES led_blinky.c
)
```

The generated board and app support files are included through:

```cmake
include(${board}/board_files.cmake)
```

The old top-level peripherals source entry was removed:

```cmake
mcux_add_source(
    SOURCES led_blinky/peripherals.c
            led_blinky/peripherals.h
)
```

That entry was wrong for a Config Tools compatible template because Config Tools generates peripherals under `frdmmcxa153/board/`.

## Updated `board_files.cmake`

`frdmmcxa153/board_files.cmake` now compiles files from the normalized folders:

```cmake
mcux_add_source(
    SOURCES board/board.c
            board/board.h
)

mcux_add_source(
    SOURCES board/clock_config.c
            board/clock_config.h
)

mcux_add_source(
    SOURCES board/pin_mux.c
            board/pin_mux.h
)

mcux_add_source(
    SOURCES board/peripherals.c
            board/peripherals.h
)

mcux_add_source(
    SOURCES app/app.h
            app/hardware_init.c
)
```

The include paths are now also clear:

```cmake
mcux_add_include(INCLUDES board)
mcux_add_include(INCLUDES app)
```

## Removed Duplicate Folders

These folders were removed because they duplicated or conflicted with the new canonical layout:

```text
new/led_blinky/
new/frdmmcxa153/led_blinky/
new/frdmmcxa153/frdmmcxa153/
```

After removal, there is no longer ambiguity about where generated files live.

## SysTick After Normalization

The current SysTick setting generated by Config Tools is:

```c
#define SYSTICK_CLK_FREQ 12000000UL
#define SYSTICK_TICKS 2400000UL
```

This corresponds to:

```text
12000000 / 2400000 = 5 Hz
```

So the SysTick interrupt fires every:

```text
0.2 seconds
```

The generated YAML metadata inside `peripherals.c` also records:

```text
reload: '0.2s'
```

Because CMake now builds `frdmmcxa153/board/peripherals.c`, this setting is actually used by the firmware.

## Build Verification

The normalized project was verified with:

```bash
cmake --preset debug
cmake --build --preset debug
```

The successful build compiled the expected normalized files:

```text
frdmmcxa153/board/board.c
frdmmcxa153/board/clock_config.c
frdmmcxa153/board/pin_mux.c
frdmmcxa153/board/peripherals.c
frdmmcxa153/app/hardware_init.c
led_blinky.c
```

This confirms that CMake and MCUXpresso Config Tools now agree on the source locations.

## How To Use This Template

### Clone the Course Repository

Start by cloning the course repository and moving into the source folder:

```powershell
git clone https://github.com/alexp25/ipcei-lab.git
cd ipcei-lab\src
```

The reusable template is stored here:

```text
src/lab_new_project/new
```

This folder is intentionally a complete, buildable FRDM-MCXA153 project. It already contains the normalized CMake layout, the `.mex` file, the generated board files, and the handwritten application glue.

### Create a New Project from the Template

To start a new lab or demo, copy only the source/configuration files from the template. Do not copy build outputs or local SDK helper folders.

Run from Git Bash, WSL, or another Bash shell after changing the destination folder from `my_new_project` to your new folder name:

```bash
#!/usr/bin/env bash
set -e

# =========================
# Configuration
# =========================

workspace_src_root="/c/WORKSPACE/proiecte/ipcei-lab/src"

src="lab_new_project/new"
dest="lab_new_project_configured/configured2"

# =========================
# Script
# =========================

cd "$workspace_src_root"
pwd

echo "Source:      $src"
echo "Destination: $dest"

if [ ! -d "$src" ]; then
  echo "Source project does not exist: $src"
  read -p "Press enter to continue"
  exit 1
fi

if [ -e "$dest" ]; then
  echo "Destination already exists: $dest"
  echo "Choose a new name or delete the old failed copy first."
  read -p "Press enter to continue"
  exit 1
fi

mkdir -p "$dest"

tar \
  --exclude='./debug' \
  --exclude='./debug/*' \
  --exclude='./__repo__' \
  --exclude='./__repo__/*' \
  --exclude='./.git' \
  --exclude='./.git/*' \
  --exclude='*.elf' \
  --exclude='*.bin' \
  --exclude='*.map' \
  --exclude='*.axf' \
  --exclude='*.o' \
  --exclude='*.obj' \
  --exclude='*.d' \
  -cf - -C "$src" . | tar -xf - -C "$dest"

ls "$dest"

old_root="$(
  cd "$src"
  pwd -W 2>/dev/null || pwd
)"

old_root_lc="$(echo "$old_root" | tr '[:upper:]' '[:lower:]')"

cd "$dest"

new_root="$(pwd -W 2>/dev/null || pwd)"

echo "Replacing:"
echo "  $old_root"
echo "  $old_root_lc"
echo "with:"
echo "  $new_root"

find cfg_tools frdmmcxa153 -type f \( -name '*.json' -o -name '*.mex' \) -print0 2>/dev/null \
  | while IFS= read -r -d '' file; do
      sed -i \
        -e "s#${old_root}#${new_root}#g" \
        -e "s#${old_root_lc}#${new_root}#g" \
        "$file"
    done

echo
echo "Checking for leftover references to source path:"
grep -RIn "$src" cfg_tools frdmmcxa153 || true

echo
echo "Done. New project created at:"
echo "$new_root"

```

Use a short folder name without spaces. This avoids path quoting problems in CMake, Ninja, the ARM GCC toolchain, and MCUXpresso Config Tools.

> Do not copy the whole template folder blindly. If the template has been built before, it may contain `debug/`, CMake output, and SDK-shaped helper folders. Copying those makes the new project huge and slow, and it can also preserve stale build paths from the old project. Also do not reuse a destination folder from a failed attempt: `tar` will not delete files that are already there.

After copying, open the new folder in VS Code:

```bash
code /c/WORKSPACE/proiecte/ipcei-lab/src/my_new_lab
```

Then build it once before changing anything:

```bash
cmake --preset debug
cmake --build --preset debug
```

A clean first build proves that the copied template is intact.

The final `grep` command should print nothing. If it still finds `lab_new_project/new`, some Config Tools metadata still points back to the original template and must be fixed before opening the `.mex` file.

### Rename the Project for the New Lab

At minimum, update the visible project names so the copied project is not still called `led_blinky` everywhere:

1. Rename the main application file if needed, for example:

   ```text
   led_blinky.c -> my_new_lab.c
   ```

2. Update `CMakeLists.txt` so it compiles the renamed source file.
3. Rename the `.mex` file if you want the Config Tools project name to match the new lab:

   ```text
   frdmmcxa153/led_blinky.mex -> frdmmcxa153/my_new_lab.mex
   ```

4. Open the `.mex` file in MCUXpresso Config Tools and verify that generated code still targets:

   ```text
   frdmmcxa153/board/
   ```

5. Rebuild after the rename:

   ```powershell
   cmake --preset debug
   cmake --build --preset debug
   ```

Do not move generated files out of `frdmmcxa153/board/`. That folder is what keeps Config Tools and CMake synchronized.

### To change pin mux, clocks, or peripherals

1. Open:

   ```text
   frdmmcxa153/led_blinky.mex
   ```

2. Change settings in MCUXpresso Config Tools.
3. Click **Update Code** or **Generate Code**.
4. Confirm that generated files changed in:

   ```text
   frdmmcxa153/board/
   ```

5. Rebuild with:

   ```bash
   cmake --preset debug
   cmake --build --preset debug
   ```

### To change application behavior

Edit:

```text
led_blinky.c
frdmmcxa153/app/app.h
frdmmcxa153/app/hardware_init.c
```

These files are project-owned application files and are not expected to be regenerated by Config Tools.

### To add new generated peripherals

Use MCUXpresso Config Tools and generate code into:

```text
frdmmcxa153/board/
```

If Config Tools creates additional `.c` or `.h` files, add them to:

```text
frdmmcxa153/board_files.cmake
```

## Template Rule

For this project template, use this rule:

> `frdmmcxa153/board/` is generated/configured board code. `frdmmcxa153/app/` is handwritten app glue. `led_blinky.c` is the main application.

That keeps the project understandable for students and keeps MCUXpresso Config Tools working predictably.
