# LP4 - Project Setup

**From project idea to scoped requirements for a summer embedded project**

---

| | |
|---|---|
| **Session** | Summer project selection and specification |
| **Board** | FRDM-MCXA153 |
| **Tooling** | Coding agent prompts, human review, MCUXpresso SDK and Config Tools |
| **Agent prompts** | `src/lab_new_project_configured/configured_project/.agents/agent_0_embedded_project_scoping.md`, `src/lab_new_project_configured/configured_project/.agents/agent_1_requirements_engineering.md` |
| **Output** | Scoping JSON file, HTML scoping report, HTML requirements report, test plan, risks, and review checklist |
| **Goal** | Choose an embedded project idea and turn it into a realistic implementation plan |

## Context

Over the summer, each student or team should implement an embedded project using the **NXP FRDM-MCXA153** board.

At the beginning, the project idea may be vague:

- "a small weather station";
- "a reaction timer game";
- "a sensor logger";
- "a USB gadget";
- "something with a display and buttons".

That is normal. The important step is to turn the idea into a scoped project that can be implemented, tested, and presented.

This lesson uses two AI-agent prompts:

1. **Agent 0** turns a vague idea into a structured JSON scoping brief and a human-readable HTML scoping report.
2. **Agent 1** turns that JSON brief into a requirements and specification package for human review.

The prompt files are in the configured project:

```text
src/lab_new_project_configured/configured_project/.agents/
  agent_0_embedded_project_scoping.md
  agent_1_requirements_engineering.md
  data/
```

The AI output is not the final authority. It is a draft. You must review it, adjust the scope, and check that the hardware and schedule are realistic.

## Workflow

Use this two-step workflow:

1. User vague idea/spec -> Agent 0 -> `.agents/data/project_scoping_brief.json` and `.agents/data/project_scoping_brief.html`
2. `.agents/data/project_scoping_brief.json` -> Agent 1 -> `.agents/data/requirements_report.html`

Agent 0 helps separate the project into:

- a **core student version** that should be achievable;
- a **recommended version** that is the normal target;
- an **advanced extension** for teams that finish early or want extra challenge.

Agent 1 expands that scope into an HTML requirements report with requirements, tests, traceability, risks, and a human review checklist.

## Rules for the Project

Every project must:

1. use the **NXP FRDM-MCXA153** board;
2. have a clear input, output, or interaction behavior;
3. include a core version that can be completed with limited time;
4. include at least one testable requirement;
5. avoid relying on invented pin names, exact pins, or SDK APIs before the project is configured in MCUXpresso Config Tools;
6. be reviewed by a human before implementation starts.

## Step 1: Scope the Idea with Agent 0

Start with a short description of the project idea. It can be informal, but it should include what the project is supposed to do, what hardware you expect to use, and what would make the demo interesting.

Examples:

- "I want to build a small reaction timer game using LEDs and buttons."
- "I want a temperature logger that shows values on a display and can send data over serial."
- "I want a USB HID device controlled by a sensor."

After Agent 0 produces the JSON scoping brief, pass the JSON file path to Agent 1.

</div>

Agent 1 should produce a self-contained HTML specification package that can be opened in a browser and reviewed before implementation. The output should help you decide:

- what the minimum working demo is;
- which features are required and which are optional;
- what needs to be configured in MCUXpresso Config Tools;
- how the project will be tested;
- what risks must be reduced early.

## Human Review

Before writing code, review the Agent 1 output.

Check that:

1. the core version is small enough to finish;
2. the recommended version is realistic for the summer project;
3. the advanced extension is clearly optional;
4. requirements are testable;
5. hardware assumptions are marked as assumptions, not facts;
6. no exact pins, interrupts, SDK function names, or peripheral instances are invented;
7. the project can be demonstrated on the FRDM-MCXA153 board;
8. the risks include hardware availability, integration complexity, debugging difficulty, and schedule.

## Deliverable

Submit or keep in your project folder:

1. the original project idea;
2. the Agent 0 JSON scoping brief file;
3. the Agent 0 HTML scoping report;
4. the Agent 1 HTML requirements report;
5. a short human review note explaining what you accepted, changed, or rejected.

This package becomes the starting point for implementation. Later, when you configure pins and peripherals, the MCUXpresso project configuration becomes the source of truth for exact hardware details.
