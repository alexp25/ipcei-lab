## Context and Motivation

This lab introduces GPIO on the MCX A family. Unlike simple 8-bit microcontrollers, pin routing and pin electrical configuration are handled by the `PORT` peripheral, while logical read/write operations are handled by `GPIO`.

That split matters in real projects: a pin can be configured correctly as a GPIO output only if both the mux and the GPIO direction/state are configured.

> **Board:** FRDM-MCXA153, MCX A153 Cortex-M33, MCUXpresso SDK, VS Code, CMake.

## Objectives

By the end of the lab you should be able to:

1. Configure GPIO pins as digital outputs.
2. Control the RGB LED channels independently.

5. Explain the difference between `PORT_SetPinConfig()` / `PORT_SetPinMux()` and `GPIO_PinWrite()` / `GPIO_PinRead()`.
6. Use MCUXpresso Config Tools and verify that generated files match the CMake build.

## How `.mex`, Config Tools, Generated Code and CMake Fit Together

The `.mex` file is not executable code. It is the model used by Config Tools. It describes:

- pin mux and electrical settings;
- clocks and dividers;
- peripherals initialized by the tool;
- generated function names and output file paths.

When you click **Update Code**, the tool writes C source files:

```text
main.mex
  |
  |-- Pins        -> board/pin_mux.c, board/pin_mux.h
  |-- Clocks      -> board/clock_config.c, board/clock_config.h
  `-- Peripherals -> board/peripherals.c, board/peripherals.h
                         |
                         `-- CMake must compile these exact files
```

Important rule:

> The `.mex` file, the generated files, and the files listed in CMake must describe the same hardware and use the same paths.

If Config Tools updates one copy of `pin_mux.c` but CMake compiles another copy, the GUI will look correct while the board still runs old code.

### Generated File Ownership

| File | Role | Owner |
|---|---|---|
| `.mex` | Config Tools source of truth | Config Tools |
| `pin_mux.c/.h` | Pin routing and electrical settings | Generated by Pins tool |
| `clock_config.c/.h` | Clock tree setup | Generated by Clocks tool |
| `peripherals.c/.h` | Peripheral instance initialization | Generated by Peripherals tool |
| `board_files.cmake` | Tells CMake what generated files to compile | Project integration |
| Application driver files | Reusable logic | Handwritten |
| `main.c` | Application behavior | Handwritten |

Generated files usually contain this warning:

```c
/* This file was generated by the MCUXpresso Config Tools.
 * Any manual edits made to this file will be overwritten. */
```

Permanent pin/clock/peripheral changes should be made through the `.mex` model, not by editing generated C only.

## Recommended Workflow for a New Peripheral

1. Identify the peripheral instance, pins, mux functions and required clocks.
2. Inspect which `.mex` file is active and which generated files CMake compiles.
3. Configure pins in Config Tools.
4. Configure clocks/peripherals only through supported GUI options.
5. Review the **Update Files** diff before accepting it.
6. Regenerate code.
7. Confirm CMake compiles each generated file exactly once.
8. Run a clean build.
9. Test on the board.

## Checklist Before Accepting Update Code

- [ ] Is the correct `.mex` file open?
- [ ] Do Config Tools and CMake use the same `pin_mux.c`, `clock_config.c`, and `peripherals.c`?
- [ ] Is the dialog changing only expected generated files?
- [ ] Is it avoiding handwritten drivers and application files?
- [ ] Are there duplicate generated files in different folders?
- [ ] Does the project still build after regeneration?

## Common Pitfalls

- `PORT` and `GPIO` are different peripherals. Enable the clock for every `PORTx` you use.
- `GPIO_PinWrite(..., 0U)` turns an active-low LED on.
- `kPORT_MuxAsGpio` values can differ between families; check `fsl_port.h`.
- Do not let AI generate Arduino or generic HAL code for this board.
- Do not accept unexpected Config Tools file moves without checking the build paths.
