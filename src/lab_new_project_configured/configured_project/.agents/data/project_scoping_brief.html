Project Summary

The project is a small autonomous vehicle controlled by the NXP FRDM-MCXA153. It follows a controlled road track, reacts to simple traffic cues, and can scale from reliable sensor-based line following to constrained TinyML vision classification.

Main objective Demonstrate embedded autonomy through motor control, road tracking, traffic cue recognition, and safe navigation in a controlled indoor environment.
Intended user Third-year university Computer Science student
Operating environment Indoor lab track with printed or taped road lines, controlled lighting, low speed operation, and instructor-approved test zones.
Main behavior The car starts safely, follows a marked road, slows or stops for recognized cues, responds to traffic signs or lights, and reports status through LEDs, serial logs, or an optional display.

Fixed Platform

Board: NXP FRDM-MCXA153

MCU: NXP MCXA153

Status: Mandatory user constraint. This board must remain the main controller.

Pin policy: Use generic capabilities such as GPIO-capable, ADC-capable, PWM-capable, I2C-capable, UART-capable, SPI-capable pins, and USB interface until exact routing is reviewed.

Logic level policy: Assume 3.3 V logic unless verified otherwise.

Ambition Levels

Core Student Version

Intermediate

Build a safe road-following rover using the FRDM-MCXA153, a small chassis, a motor driver, reflectance or line sensors, and simple cue handling through colored markers or predefined stop zones.

  • Two-wheel differential drive or equivalent low-speed chassis control
  • Line or road following using reflectance sensors or simple thresholded sensing
  • Start, stop, calibration, and emergency fault states
  • Basic speed control using PWM-capable outputs through a motor driver
  • Road-lost detection with safe stop behavior
  • Serial debug logs and status LED feedback

Suitable because it teaches GPIO, timers, PWM, calibration, state machines, control loops, and safe hardware integration without depending on difficult camera performance.

Recommended Summer School Version

Advanced but feasible

Add constrained computer vision and TinyML classification for a small set of traffic signs or traffic light colors while keeping road following sensor-assisted and the environment highly controlled.

  • Low-resolution camera module with verified 3.3 V logic or proper level shifting
  • TinyML classifier for limited classes such as stop, speed marker, arrow, red light, and green light
  • Sensor-assisted road following so vision is used for decisions rather than all steering
  • Confidence thresholding with unknown or low-confidence fallback behavior
  • Behavior mapping from detected cue to stop, slow, turn, or continue
  • Dataset capture workflow and repeatable lab lighting assumptions

Interesting because it makes the self-driving idea real while exposing microcontroller limits: tiny images, small models, deterministic control, power limits, and safety fallback states.

Advanced Extension

Optional advanced

Extend the recommended prototype with richer navigation, better TinyML validation, data logging, obstacle handling, and GenAI-assisted development artifacts.

  • More traffic sign classes with an explicit unknown class
  • Traffic light recognition using color regions or TinyML
  • Obstacle stop or slow-down behavior using a distance sensor
  • Lap, route, or intersection state machine
  • Inference, sensor, motor, and failure data logging
  • PC-side dataset review and confusion matrix generation

Risk controls include low vehicle speed, physical or firmware stop behavior, 3.3 V verification, separate motor power, and treating advanced work as optional.

Power and Safety

Important: Motors, camera modules, and optional sensors may require power beyond what the board or USB path can safely provide. Motors must use an external driver and suitable supply. Do not assume 5 V compatibility with MCU signals.

  • Use USB or normal board development power for FRDM-MCXA153 logic during bring-up.
  • Use a separate regulated motor supply for the chassis if required by the motors and driver.
  • Review common ground, current limits, polarity, and protection before connecting power domains.
  • Keep vehicle speed low and test in an instructor-approved area.
  • Implement stop behavior before autonomous driving tests.

Assumptions

  1. The vehicle will be a small tabletop or floor robot, not a road-capable vehicle.
  2. Road following can be implemented with line or reflectance sensors in the core version.
  3. TinyML classification will be limited to a small number of traffic signs or traffic light states.
  4. The camera module and motor driver will be selected later based on 3.3 V logic compatibility and local availability.
  5. The controlled environment will have consistent lighting and printed or taped road features.

Open Questions

Q-001 Which chassis, motors, motor driver, and power source are available? Determines speed control method, power safety requirements, and hardware integration effort.
Q-002 Which camera module is available and compatible with the FRDM-MCXA153 setup? Camera interface, frame size, buffering, and SDK support determine whether TinyML vision is feasible.
Q-003 How many traffic signs and traffic light states must be recognized? Class count affects dataset size, model complexity, memory use, and testing effort.
Q-004 Will students train a model before the lab or during the course? TinyML preparation can dominate schedule if dataset capture and training are not planned early.
Q-005 What safety rules apply to moving robots in the lab? Speed limits, test area rules, and emergency stop expectations should become requirements.
Q-006 Should traffic light recognition use camera color detection, a separate color sensor, or encoded lab fixtures? The answer changes sensor selection, difficulty, and robustness.

Risks

Technical

  • Full camera-based steering and sign recognition may exceed schedule and compute budget.
  • Camera integration may be harder than line sensor and motor control integration.
  • Offline model accuracy may fail on the moving car due to blur, angle, or lighting.

Voltage and Power

  • Modules may not be 3.3 V logic compatible.
  • Motor current can exceed USB or board power limits.
  • Voltage dips and motor noise can reset the MCU.

Timing and Memory

  • TinyML inference may block the control loop if scheduled poorly.
  • Image buffers, model weights, tensor arenas, and logs can exceed memory if image sizes are too large.
  • Storage, display, and telemetry features reduce resources available for inference.

Safety and Privacy

  • Low speed, supervised testing, and stop behavior are required.
  • Datasets should avoid identifiable people and private spaces.
  • Wireless telemetry should not be treated as secure without explicit design work.
